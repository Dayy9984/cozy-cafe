그렇다면 **제가 앞에서 설명한 방식은 지금 팀에는 과합니다.** 3명 전원이 첫 게임 개발이고, 소규모 방치형 인디게임이라면 대형 스튜디오식 `GDD/TDD/Scrum/수십 개 문서`를 따라 하면 오히려 개발보다 관리에 시간을 더 쓰게 됩니다.

Unity의 소규모 게임 제작 교육도 핵심 기능·에셋 목록을 우선순위화하고, 백로그를 만든 뒤 프로토타입과 작은 Vertical Slice를 실제 빌드로 검증하는 흐름을 사용합니다. :chatgpt-content-reference{index="0"}

당신들한테는 **문서 5개 + 작업보드 1개 + 매주 빌드 1개**면 충분합니다.

# 1. 우선 3명을 이렇게 생각하세요

회사처럼

> 기획팀 / 아트팀 / 개발팀

이라고 생각하면 안 됩니다.

실제로는:

| 사람 | 주 역할 | 부 역할 |
|---|---|---|
| 당신 | **PM + 게임기획** | 데이터 입력, QA, 일정, 레퍼런스 |
| A | **프로그래머** | 기술검토, 빌드, 아트 Integration |
| B | **아티스트** | UI/도트/애니메이션 |

정도입니다.

그리고 의사결정 구조는:

```text
게임 방향 / Scope
        ↓
    당신(PM/기획)
        ↓
 ┌─────────────┐
개발 가능?     아트 가능?
 개발자         아티스트
 └──────┬──────┘
        ↓
     결정
        ↓
    실제 Build
```

입니다.

당신이 개발자에게

> 이거 2일 안에 해주세요.

라고 일방적으로 정하는 것이 아니라,

> 이 기능이 필요하다.
> 이번 마일스톤에 반드시 필요하다.
> 어느 정도 작업일 것 같나?

라고 물어봅니다.

개발자가

> 처음 해보는 기능이라 정확히 모르겠지만 2~4일 정도 같습니다.

하면 PM이

> 그럼 4일로 잡고, 이번 주 다른 기능 하나를 뒤로 미루자.

하는 구조입니다.

**PM이 일정을 만들어내는 게 아니라 팀의 작업량을 가지고 일정을 조립하는 겁니다.**

# 4. 문서 1 — Game Overview

**1~3페이지를 넘기지 마세요.**

여기가 모든 판단의 기준입니다.

당신들 게임이라면 이런 형태입니다.

## GAME OVERVIEW

### 게임 한 줄 설명

카페가 자동으로 운영되고, 플레이어가 성장 요소를 해금하며 카페가 점점 확장되는 도트 그래픽 방치형 게임.

### 장르

```text
Idle / Incremental
+ Café Theme
```

### 가장 중요한 경험

```text
가만히 보고 있어도 카페가 계속 돌아간다.

조금씩 더 많은 메뉴와 기능이 열리면서
카페가 발전하는 모습을 보는 재미.

복잡한 경영게임이 아니라
간단하게 개입하면서 성장시키는 방치형 게임.
```

### Core Loop

```text
손님 등장
↓
주문
↓
직원/머신을 통해 제작
↓
제공
↓
보상
↓
성장/연구/해금
↓
더 많은 주문 처리
↓
반복
```

### 게임의 원칙

예:

```text
1. 방치형 게임이다.

2. 복잡한 타이쿤 시뮬레이션으로 만들지 않는다.

3. 플레이어가 시스템을 세세하게 관리해야 하지 않는다.

4. 카페가 자동으로 움직이는 모습을 보는 재미가 중요하다.

5. 콘텐츠 종류 증가보다 조합과 반복으로 볼륨을 만든다.
```

### 만들지 않는 것

이게 특히 중요합니다.

현재 결정된 것을 여기에 박아놓습니다.

```text
X 손님 도감
X 직원 도감
X 복잡한 재료 구매 경제
X 복잡한 타이쿤 경영
X 머신 종류 무한 추가
X 지나치게 세밀한 직원 관리
```

현재 계획대로라면 머신은 스팀기, 믹서기, 제빙기, 그라인더, 에스프레소 머신 정도의 고정된 범위를 활용하고, 손님과 직원은 수집형 개체를 계속 만드는 대신 프리셋·색상·스탯 조합으로 다양성을 만드는 방향이므로 이런 결정은 Overview에 고정해 두는 게 좋습니다. 

이게 있어야 한 달 후 갑자기 게임이 타이쿤으로 변하는 것을 막습니다.

# 5. 문서 2 — Feature List

이게 사실상 여러분의 **간이 GDD**입니다.

스프레드시트 한 장이면 됩니다.

예를 들어:

| ID | 기능 | 우선순위 | 상태 | 기획 | 개발 | 아트 |
|---|---|---|---|---|---|---|
| F001 | 시간 진행 | Must | Todo | Ready | Todo | - |
| F002 | 손님 생성 | Must | Todo | Ready | Todo | Todo |
| F003 | 주문 생성 | Must | Todo | Ready | Todo | UI |
| F004 | 메뉴 데이터 | Must | Todo | WIP | Todo | Todo |
| F005 | 메뉴 제작 | Must | Todo | WIP | Todo | Todo |
| F006 | 머신 | Must | Todo | WIP | Todo | Todo |
| F007 | 직원 | Must | Todo | WIP | Todo | Todo |
| F008 | 돈 | Must | Todo | Ready | Todo | UI |
| F009 | 연구 | Should | Backlog | Todo | Todo | UI |
| F010 | 도전과제 | Could | Backlog | Todo | Todo | UI |

그리고 우선순위는 딱 세 개만 쓰세요.

### Must

없으면 게임 자체가 안 됨.

### Should

게임에는 필요하지만 Prototype에는 없어도 됨.

### Later

나중에 판단.

`Could`, `Won't`, `P0`, `P1`, `P2`, `Critical`, `Major` 같은 분류를 여러 개 만들 필요 없습니다.

# 6. 특히 초보 팀은 Feature List를 계속 줄여야 합니다

아이디어가 떠올랐다고:

```text
아이디어
↓
Feature List
```

로 바로 넣으면 안 됩니다.

중간에 하나를 둡니다.

```text
IDEA BOX
```

예를 들어 누군가

> 날씨에 따라 손님이 달라지는 건 어때?

라고 한다면 바로 개발하지 않습니다.

```text
IDEA
날씨 시스템
```

이라고만 기록합니다.

그리고 주 1회 셋이서 봅니다.

> 우리 게임에 정말 필요한가?

필요 없음:

```text
Discard
```

재미있지만 지금 필요 없음:

```text
Later
```

반드시 필요:

```text
Feature List
```

이렇게 합니다.

**아이디어와 할 일을 분리하는 것**이 PM의 첫 번째 중요한 역할입니다.

# 7. 문서 3 — Feature Spec

이것도 기능 하나당 한 페이지씩 쓰지 않아도 됩니다.

Notion 페이지든 표든 상관없습니다.

간단한 기능은 10줄이면 됩니다.

예를 들어:

## F003 주문 생성

### 목적

손님이 일정한 메뉴를 주문한다.

### 발생 조건

손님이 주문 위치에 도착.

### 처리

```text
손님 도착
↓
가능한 메뉴 목록 확인
↓
메뉴 하나 랜덤 선택
↓
Order 생성
↓
주문 Bubble 표시
```

### 필요한 데이터

```text
Customer ID
Recipe ID
Order State
```

### 완료 조건

```text
□ 손님이 주문할 수 있다.
□ 메뉴가 표시된다.
□ 주문 데이터가 생성된다.
□ 주문이 끝나면 사라진다.
□ 오류 없이 다음 손님이 주문한다.
```

끝.

개발자가 이것을 보고 이해하면 충분합니다.

# 8. 복잡한 기능만 조금 길게 씁니다

예를 들어 **방치 보상**은 중요하고 복잡하므로 더 상세하게 작성합니다.

## Offline Progress

### 목적

게임을 종료해도 카페가 일정 부분 진행된다.

### 저장

```text

현재 생산 상태
현재 자원
```

### 게임 재실행

```text
현재 시간
-
LastExitTime

= Offline Time
```

### 계산

```text
Offline Time
×
생산 속도
=
Offline Production
```

### 제한

예:

```text
최대 8시간
```

같은 정책이 있다면 기획에서 결정합니다.

이 정도면 개발자가 구현 방법을 설계할 수 있습니다.

**기획서에 코드 구조까지 쓰지 마세요.**

그건 개발자가 결정해야 합니다.

그리고 머신도 필요한 종류 일부를 붙입니다.

> 새로운 메뉴 추가할 때 프로그래머가 코드를 계속 수정해야 하는가?

입니다.

가능하면:

```text
RecipeData

Name
Sprite
Machine
Duration
Reward
```

처럼 만들어서

**기획자가 데이터 입력만 하면 메뉴가 늘어나는 구조**

로 만드세요.

이건 앞으로 개발 시간을 엄청 줄여줍니다.

---

# 18. 그다음 처음으로 진짜 아트를 붙입니다

여기가 여러분의 **Vertical Slice**입니다.

Prototype과 다릅니다.

Prototype:

> 게임이 작동하는가?

Vertical Slice:

> 우리가 생각하는 최종 게임을 실제 품질로 만들 수 있는가?

Unity도 소규모 게임의 마일스톤 학습 과정에서 핵심 기능과 필요한 에셋을 정하고 이를 Vertical Slice로 만들어 보는 방식을 사용합니다. :chatgpt-content-reference{index="4"}

# 21. 그래서 첫 6주를 이런 식으로 보내는 걸 권합니다

### 1주차 — 게임 고정

# 31. 그래서 지금 당장 해야 할 일은 이것뿐입니다

**1단계**

당신이 `Game Overview`를 작성합니다.

**2단계**

세 명이 모여 전체 기능을 `Must / Later`로 나눕니다.

**3단계**

게임 전체를 만들려고 하지 말고:

> 손님 1 → 주문 1 → 머신 1 → 돈

만 구현합니다.

**4단계**

아티스트는 동시에 최종 그림을 잔뜩 만들지 말고

> 캐릭터 하나 + 머신 하나

로 Art Pipeline을 테스트합니다.

**5단계**

매주 금요일 실제 빌드를 실행합니다.

**6단계**

Vertical Slice를 완성한 이후 실제 제작 속도를 기반으로 전체 게임 규모와 출시 일정을 결정합니다.

## 그리고 당신의 PM 업무를 극단적으로 요약하면

```text
             IDEA
               ↓
        지금 필요한가?
          ↙         ↘
        NO          YES
        ↓            ↓
      Later     Feature Spec
                     ↓
              작업으로 분해
                     ↓
          ┌──────────┴──────────┐
         Art                  Dev
          └──────────┬──────────┘
                     ↓
                  Build
                     ↓
                 Playtest
                     ↓
              문제 / 개선점
                     ↓
                  Backlog
```

이 흐름만 제대로 운영해도 첫 프로젝트 PM으로서는 충분합니다.

**3명짜리 첫 방치형 게임에서 성공적인 PM은 복잡한 개발 방법론을 적용하는 사람이 아니라, 게임의 범위를 계속 작게 유지하고, 세 사람이 다음에 해야 할 일이 무엇인지 모르는 순간이 없게 만들고, 매주 실제로 돌아가는 게임을 만드는 사람입니다.**

특히 현재 프로젝트라면 이제 아이디어를 더 확장하는 것보다 **Game Overview → 전체 Feature List → Prototype 0 범위 확정 → 3명 각각의 첫 작업 목록** 순으로 넘어가는 게 맞습니다. 여기까지 정리되면 그 다음부터는 지금 가지고 있는 게임 아이디어를 실제 작업 티켓 수준으로 하나씩 분해할 수 있습니다.
